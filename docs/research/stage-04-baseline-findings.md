## K04 — six answers bounded by source

1. **Does Pear intentionally equate zero and mute?** Not established. The checked-in API code does not compute mute as `volume === 0`. Its dynamic YouTube Music player may couple them, but its current native implementation is not contained in this checkout.
2. **Separate observable flag?** Yes: `song-info-front.ts:setupVolumeChangedListener` sends `{state: api.getVolume(), isMuted: api.isMuted()}` on volumechange and initially. REST GET volume forwards that cache; WS sends `{volume, muted}`. A separate field exists, though source does not prove every combination is physically reachable.
3. **API genuine mute or UI-only zero icon?** API forwards native `isMuted()`, not the UI icon. The Windows report captures UI behavior, not a synchronized API/WS sample, so the failed scenario does not establish what `isMuted` actually reported. Cold REST fallback `{state:0,isMuted:false}` is not proof of a live zero/unmuted state.
4. **5% unmute intentional?** `song-controls.ts:muteUnmute` → `peard:toggle-mute` → `src/renderer.ts` calls native `ytmusic-player-bar.onVolumeClick()`. There is no explicit five-percent unmute policy in this path. The external-volume helper's minimum slider display of 5 for values 1–4 is UI synchronization, not evidence that it implements unmute restoration. Neither deliberate design nor a Pear defect is proved.
5. **Can plugin distinguish the two zero states?** It can distinguish them *if* the native API emits distinct `isMuted` flags: `state.ts:parseStateResponse` copies the boolean and key rendering uses `state.muted`, never deriving it from volume. `commands.ts:toggleMute` confirms the opposite native mute flag; it does not invent a target or restoration level.
6. **Is expectation achievable?** Logically representable in the API, physically reachable at zero remains unproved. The test's wording must not be replaced with a guessed volume-based mute rule. Keep historical Fail and unchanged definition until focused native/API comparison resolves the reachable contract.

Automated `tests/pear-key-actions.test.ts` supplies synthetic zero/false and checks no inferred mute; this proves plugin mapping, not that native Pear can produce it. Classification: insufficient evidence, with Pear-native/API semantics investigation first. No catalog version change justified yet.

## P01 — full request path and 503 inventory

`PearKeyActions.press` → `PearClient.startPlaylist` → input normalization/mode capture → shared `request('POST','play-playlist',{playlistId,shuffle},200)` → `PearRestClient` bearer JSON request → Pear API auth middleware → `routes/playlist.ts` → `PlaylistBroker.start` → renderer IPC start → `PlaylistAdapter` readiness → signed-in `app.networkManager.fetch('/browse',{browseId:'VL'+id})` → `resolvePlaylistCommand` (requested header/entity native normal/shuffle control) → main-process permit/auth/lifetime recheck → `guardNormalStartup` → single native `yt-action` dispatch → result IPC → broker HTTP response.

The route's declared 503 code is **PLAYER_NOT_READY**. Body is `{error:{code:'PLAYER_NOT_READY',dispatch:'not_dispatched'|'unknown'}}`. Default is not_dispatched; cancellation/result after permit is conservatively unknown. The report contains neither body nor lifecycle timing, so it cannot locate the actual branch. Every explicit route/broker/adapter path yielding this status is inventoried below; multiple branches intentionally share the code.

| Source / branch | Condition and interpretation | Dispatch |
| --- | --- | --- |
| `routes/playlist.ts` initial enabled check | Auth succeeded, but config says API disabled while request is being served; API lifecycle, not a playlist visibility conclusion. | not_dispatched |
| `playlist-broker.ts:start` /`available` | Broker disabled/disposed or BrowserWindow/webContents destroyed. Renderer/broker unavailable. | not_dispatched |
| `start` aborted signal /abort listener | Already-aborted HTTP request, or subsequent HTTP abort while pending. Transport/lifetime cancellation. | not_dispatched before permit; unknown after |
| `start` send catch | `webContents.send(start)` throws; renderer transport unavailable. | not_dispatched (no permit yet) |
| `reset` → `cancel` | Called from resume/suspend/dispose, API config change/rebind/end, non-in-place main-frame navigation, renderer gone/destroyed, window closed. Superseded lifetime/generation. No pending request means no response to emit. | depends on permit |
| `onPermit` getConfig catch | Failed config read before granting permit; broker/config unavailable. | not_dispatched |
| `onPermit` config disabled | API disabled during native resolution, before permit. Auth failure instead returns 401. | not_dispatched |
| `onResult` failure forwarding | Valid correlated main-frame adapter result code PLAYER_NOT_READY is mapped through `playlistErrorStatus`; not an additional independent root cause. | unknown if already permitted; otherwise not_dispatched |
| `playlist-adapter.ts:onStart` initial check | Missing app/network manager, disconnected/replaced app, or false supplied player-ready predicate before deadline (ready also guards pending identity and enabled state). Player/adapter unavailable. Disabled/unregistered listener alone generally produces deadline 504, not an immediate 503. | normally not_dispatched |
| Adapter after browse readiness check | App/player/readiness/lifetime changed during lookup; `reportUnavailable` emits PLAYER_NOT_READY before deadline. Cancellation that already cleared pending emits nothing new. | before permit |
| Adapter after permit await | Permit absent/denied, or readiness/app identity lost before dispatch; same `reportUnavailable` before deadline. Broker may already have finalized a different status. | broker tracks permitted; may be unknown |

Deadline branches use **504 PLAYLIST_START_TIMEOUT**, not 503. Invalid payload is 400, busy 409, explicit unavailable/unplayable/native account errors 422, unsupported/missing/ambiguous control or no native dispatcher 501, browse/lookup failure 502 PLAYLIST_RESOLUTION_FAILED, dispatch exception after permit 502 PLAYLIST_DISPATCH_FAILED, auth/principal change 401. `playlist-command.ts` has no PLAYER_NOT_READY throw. Even an upstream browse HTTP 503 thrown as an ordinary fetch error maps to **502** here; it is not automatically the extension's outgoing 503. No custom route catch remaps all exceptions to 503; unhandled exceptions are not a confirmed explanation for the observed status.

**Priority hypothesis, not a proven defect:** `api-server/renderer.ts` requires `#movie_player === this.player`, a function `current.isReady`, and `current.isReady() === true`. `MusicPlayer`'s checked-in type does not declare isReady. The native website is dynamic: absence/different return value or missing lifecycle callback can reject an apparently playing player. `src/renderer.ts` does forward `onPlayerApiReady` on initial load and plugin re-enable, so a missing re-enable hook must not be asserted without measurement. `tests/api-playlist-fixtures.ts` injects a ready callback into the adapter; fixture passes do not verify that actual DOM/player predicate on Windows. Next diagnosis must sample those booleans safely and distinguish them from lifecycle/config/broker branches.

**Plugin observability:** REST reads at most 1,024 bytes of playlist error JSON and keeps only allowlisted code/status/dispatch in `PearRequestError.playlistFailure`. Recognized unknown dispatch becomes `PearPlaylistError('unconfirmed')`; recognized not_dispatched 503 remains generic `Pear request failed (HTTP 503).` Key/dial render Start failed and PI shows the safe error message; normal logs say only “Pear request failed; confirmed player state was retained.” The raw/native/account body is intentionally discarded. Thus code/outcome are preserved internally for control flow, but neither safe PLAYER_NOT_READY nor its particular branch is normally shown to the user. A generic 503 message could also mean an unrecognized/malformed body, so it must not be interpreted as proof of not_dispatched. No telemetry in the supplied report identifies a branch. This is a diagnostic limitation, not proof of the underlying runtime defect.

**Focused next packet:** retain loaded signed-in player and known playable public playlist; record actual installed revisions and API-enabled state. Perform one explicit normal-start attempt, capture only HTTP status + allowlisted `{code,dispatch}`, and note whether native playback/queue changed. In local Pear developer tools, record only booleans/types for app presence/isConnected/networkManager.fetch, player presence/identity/lifecycle callback and native isReady function/return. Do not copy DOM/native responses, tokens, request Authorization headers or account payloads. If body is not the contract above, establish which server/build answered before blaming this extension. If identical code remains ambiguous, a later narrowly authorized diagnostic patch should emit a bounded branch label/readiness booleans without changing startup logic.
